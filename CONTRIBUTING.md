# Contributing to Tabular UI

Tabular UI is a design system: one token layer, 18 foundational components, 26 product components, and the apps built on them. This guide is for people, designers and developers alike. `CLAUDE.md` holds the same rules written for AI agents, plus the failure log; when the two seem to disagree, `CLAUDE.md` and the spec win, and this file should be fixed.

## Read first

- **`docs/design-system.md`**: the spec, with rules, measured values, and why. §0 is the ten rules that fail review. §10 is the checklist for UI changes.
- **`docs/components.md`**: every component that exists. Check it before building anything: what you need may already be there.
- **`tools.md`**: stack, commands, and how CI behaves.
- **`CLAUDE.md`**: the failure log at the end is the fastest way to learn what has already gone wrong once.

## Set up

Node 22 (`.nvmrc`) and **pnpm only**. Never `npm` or `yarn`: a second lockfile breaks installs for everyone.

```bash
pnpm install
pnpm storybook        # every component, dark and light, on :6006
```

`pnpm install` also installs a pre-commit hook that formats the code files you commit with Prettier.

## Layout

```
packages/ui/                       the tabular-ui package: components and tokens
  src/styles/theme.css             token layer: the source of truth for values
  src/styles/palette.css           the Riso Ledger ramps, generated by scripts/generate-palette.mjs
  src/styles/shadcn.css            aliases shadcn variable names to Tabular UI tokens
  src/components/foundational/     the 18 primitives; changes here are system-level
  src/components/product/          domain composites, built from the primitives
  src/fixtures/                    story data only: Kasane fixtures, a11y exceptions
  src/index.ts                     public export surface
  scripts/build-registry.mjs       writes registry.json and the shadcn registry
apps/storybook/                    Storybook config; serves the registry at /r
  tests/                           Playwright specs; stories are their fixtures
  tests/visual.spec.ts-snapshots/  approved screenshots, one per story per theme
apps/demo/                         the Kasane onboarding demo, built on the package
  data/                            its JSON fixtures, generated
brand/                             the wordmark and favicon, used unchanged
lint/                              the design-system lint rules (CSS half, shared scale list)
eslint.config.js                   the design-system lint rules (class-string half)
docs/                              spec, component inventory, agent voice, palette
```

Every component lives in its own folder with three files: `index.tsx` (props carry JSDoc), `README.md` (when to use it, and the decisions behind it) and `[Name].stories.tsx` (every state). Each component's **Docs** page in Storybook lists its props, generated from the types.

## Commands

From the repo root:

```bash
pnpm storybook          # Storybook on :6006, light/dark toggle in the toolbar
pnpm dev                # the demo, with the package rebuilding on change
pnpm lint               # ESLint + Stylelint + Prettier, fails on any warning; run first
pnpm typecheck          # every workspace package
pnpm test               # every story rendered in headless Chromium, with axe, in both modes
pnpm test:playwright    # browser specs: focus rings, contrast, keyboard, layout
pnpm test:visual        # screenshot comparison (Linux only; runs in CI)
pnpm build              # the package, the registry, Storybook, then the demo
```

`pnpm test` downloads Chromium on first run.

## The rules that most often fail review

The full list is §0 of the spec. These are the ones new contributors hit:

- **Colour means state, never hierarchy.** Labels, headers, dividers and secondary buttons stay neutral. A hue appears only when something is true about the data, the run, or the user's focus.
- **Five hues, no sixth.** Compose a new state from the five plus shape, weight, icon or a neutral tint.
- **Reach for the semantic token first.** `--pad-cell-x`, not `p-2`; `--color-text-danger`, not `text-vermilion-400`. Never a raw hue in a component.
- **Caps are the design.** No component spacing above 32px, radius above 8px, or control height above 36px. Font weight never above 600.
- **Every number carries `tabular-nums`.**
- **Never re-implement a primitive inline.** A table row that needs a different button gets a `Button` variant, not a styled `<button>`. Agent-authored content always goes in `AgentBlock`.

`pnpm lint` enforces most of these. It is the first thing to run.

## Ask before you…

Some changes affect every screen at once. Talk to the design system owner (currently @pascochen) before you:

- create a **foundational** component, or change one in `packages/ui/src/components/foundational/`
- add a **token** of any kind (the spec section is written and approved first; `theme.css` is then edited to match, never regenerated)
- add a **dependency**, or edit a `package.json`, the lockfile or CI

And never rename a token: add the new one and deprecate the old.

**Product components** in `packages/ui/src/components/product/` are different: build them freely, from foundational ones, after checking `docs/components.md`. Each lives in its own folder with `index.tsx`, `[Name].stories.tsx` and `README.md`, is exported from `src/index.ts`, and needs a one-line description in `scripts/build-registry.mjs` (the registry build stops without one).

## Making a change

1. **Branch from `main`.** One change per PR; small is easier to review.
2. **Check locally**, in this order:

   ```bash
   pnpm lint              # design-system rules and formatting; fails on any warning
   pnpm test              # every story, dark and light, with accessibility checks
   pnpm build             # type-check and build everything
   pnpm test:playwright   # focus rings, contrast, keyboard, layout
   ```

   Screenshot comparison (`pnpm test:visual`) only runs on Linux, so CI does it for you.
3. **For a UI change, run the §10 checklist** in `docs/design-system.md`, and look at the stories in both modes. Some checks need a person: say which ones you did and which you didn't.
4. **Update the docs the change touches**: the component's `README.md`, `docs/components.md`, the spec if a rule changed.
5. **Open a PR.** The template asks for what reviewers need.

## CI

Every PR runs one check, **Verify** (`.github/workflows/ci.yml`), in order:

1. **Lint**: the design-system rules (no raw colours or hue names in components, the spacing, height and radius caps, outline-only focus rings, font weight ≤ 600, `tabular-nums` on metric figures) and formatting.
2. **Type-check** every workspace package.
3. **Story tests**: every story renders, in dark and in light, and passes axe accessibility checks in both. A violation fails the build. The few stories excused from one rule are listed, with the reason, in `packages/ui/src/fixtures/a11y-exceptions.ts`.
4. **Build**: the package, the registry, Storybook, then the demo against the built package.
5. **Playwright specs**: what only a real browser can measure: focus-ring clipping, computed contrast, keyboard paths, layout geometry.
6. **Visual regression**: every story screenshotted in dark and light at 1280×800, compared pixel for pixel with the approved screenshots.

**A PR that changes only Markdown files** (`.md`: READMEs, `docs/`, `CLAUDE.md`, `tools.md`) skips it all and passes in about a minute, since nothing in the build reads a `.md` file. Anything else, and every merge to `main`, gets the full run, about 20 minutes. **Don't re-run a failed Verify to see if it goes away**: understand the failure first.

## Visual changes

CI screenshots every story, dark and light, and compares each with its approved image. There are two ways for a change to be approved.

### Declared before you push

If you know which components will look different, say so in the PR description, under a **Visual changes** heading, one story file per bullet:

```md
## Visual changes

- Dialog
- AppShell: the peek's overlay sheet
- foundational/Menu
```

A bullet names a story file by its component name, folder or path; anything after it is a note. `None` declares nothing. A declaration covers the whole file, both modes, and a new story in it.

When only declared files change, Verify passes and a **Visual changes** job commits the new screenshots to your branch and marks that commit Verify ✓. No label and no second run. It also comments on the PR with:

- **Accepted**: what it committed. Review the images in the Files tab: that is approving the new look.
- **Declared, no change**: files you expected to change that didn't. Either the change doesn't show, or no story shows it: a gap in coverage.
- **Not a story file**: names that matched nothing.

GitHub still lists "1 workflow awaiting approval" for the robot's commit. It can be left; approving it only runs Verify again.

Rules that keep a declaration a prediction, not an approval:

- It is read from the description **as it was when you pushed**. Editing it takes effect on the next push, and re-running a failed Verify reads the old one.
- **Once a file has changed without a declaration on a PR, declaring it later doesn't count.** It needs the label, even for later changes on that PR.
- If anything undeclared changed, nothing is committed, declared or not.
- A story that renders differently in two screenshots of one run is never accepted.

### Reviewed after a failure

If **Visual regression (screenshots)** fails, a component looks different from its approved screenshot and nobody said it would.

1. Open the PR's failed run, download the `visual-diff-report` artifact, and open `index.html`. Each changed story shows expected, actual and a diff. The PR comment lists which files need your review.
2. **Not intended?** It's a regression: fix the code.
3. **Intended?** Add the `update-visual-baselines` label to the PR. A workflow regenerates the screenshots and commits them to your branch. Review that commit's images in the PR's Files tab: approving them is approving the new look.
4. The PR then shows **"1 workflow awaiting approval"**. Click **Approve workflows to run**: that is Verify for the new commit, and the PR is ready to merge when it is green on the PR page.

A new story needs one or the other: CI never writes a screenshot of a story nobody declared, so a story without one fails until its baseline is approved.

Baselines are Linux-only, because fonts render differently on a Mac, so `pnpm test:visual` skips on macOS. Locally, review changes in Storybook in both themes.

## Merging

- **GitHub enforces the gate.** A ruleset on `main` accepts changes only through a pull request, once Verify has passed on its latest commit and the branch is up to date with `main`. If `main` moved while you waited, use "Update branch" and let Verify run again. Nobody can push to `main` directly, the owner included. No approving review is required yet.
- **Squash merge** (the only method allowed), so `main` gets one commit per PR, titled "Summary (#123)".
- **Never write GitHub's skip-CI marker** (square brackets around "skip ci") anywhere in a commit message or PR title. A squash merge copies it into `main` and skips CI there too.

## Releases

There are none (owner, 2026-10-28). Tabular UI is a design system showcase, not a package teams depend on. Components install as source from the shadcn registry at tabularui.com, which is rebuilt from `main` on every deploy, so a merged change is out as soon as the site deploys. `packages/ui` is private, so it can't be published by accident. Version 0.1.0 stays on npm as an early snapshot and isn't updated.

## Dependency updates

Dependabot opens grouped update PRs every Monday. They go through Verify like any other PR. `tools.md`, "Dependency updates", says how to review one, including what to do when a dependency changes how something renders.

## When something goes wrong

If a mistake ships, fix it and add one entry to the failure log at the end of `CLAUDE.md`: what happened, why nothing caught it, and the rule that stops it next time. That log is how this system gets better.

## Writing product copy

Text the product's agents generate follows `docs/agent-voice.md`. In any UI text, avoid marketing words: "seamless", "unlock", "empower", "simply", "just", "easy".
