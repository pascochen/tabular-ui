### The decisions in full

**D1. Status words — decided 2026-10-25 (owner).** The wireframes' "Status words" table ("Needs your review", "Needs your answer", "Thinking…", "Searched 3 files", "Posted") mixes three vocabularies, and each already has an owner in the library:

| Vocabulary | Owner | Words today |
|---|---|---|
| Statuses: the state of a run or an item | `runStatuses` (`StatusBadge/statuses.ts`) | queued, running, passed, failed, stale, needs review, AI working (agent working until #4), proposed, skipped |
| Activity lines: what is happening now | `AgentReasoning`, `ChatThread`, `AgentPlan`; `docs/agent-voice.md` "Fixed strings" | Thinking…, Thought for 4s, Working…, Drafting step 3… |
| Authorship labels: who wrote it, and its state | `AgentBlock`'s `authorship` prop; `docs/agent-voice.md` | AI · Awaiting review, Generated by AI |

Three decisions:

1. **The site's words come from the components.** The Vocabulary page shows the three vocabularies, each from its owner, and the site invents no status word of its own. "Needs your answer" and "Searched 3 files" wait until a component says them.
2. **Principle 3 is reworded, and the library label `agent working` becomes "AI working".**
   - The wording "Status labels name the state, never the agent" was looser than its own target. Its "Instead of" column is sentences that make the agent their subject.
   - `docs/agent-voice.md` rule 1 asks agent work shown outside the rail, as in a run log, to carry the actor "AI".
   - Since the spinner replaced the robot icon (2026-10-20), the word is the badge's only authorship signal besides colour.
   - New principle: **"Status labels name the state. A role tag may say who, as AI; the agent is never a sentence's subject."**
   - "AI working" uses the one word the voice rules give the role, where the label used "agent".
   - This is a library change and its own PR: the label in `statuses.ts`, `docs/design-system.md` §5's table, the `StatusBadge` README and stories, and the screenshots it changes. The status key `agent-working` stays.
3. **A posted entry is shown by its authorship label, not a new status.**
   - When a person posts, `AgentBlock`'s label goes from "AI · Awaiting review" to "AI · Posted". That's the "role, or role plus state" form `docs/agent-voice.md` already defines, so the library needs no change.
   - The run log row written after posting uses `passed` for the step that ran.
   - The library still has no lifecycle for an entry. If a screen ever needs "posted" or "rejected" as badges, that's a new library decision.

**D2. The before/after pair — decided 2026-10-25 (owner).** The Agent block wireframe (`78:595`) heads its two plates "Agent mark" (orchid) and "Person mark" (sage). The library gives no colour to a person, and sage already means success and links (`docs/design-system.md` §1). The two colours are the wordmark's, which §1 "Brand assets" says nothing may be derived from.

The headings also implied that approval hands an entry over to the person. Books record both the preparer and the approver, and keeping them apart is the control. Kasane's own data has the failure: JE-KUK-2608-00055 was created and approved by one person (`apps/demo/data/findings.json`, `self-approved-entry`). Authorship doesn't wash off when a person approves.

1. **No plate headings.** Each block's own label carries its state. One caption under the pair, for example "The same entry, before and after a person posts it." Screen readers tell the plates apart by the labels.
2. **The posted block shows both people.**
   - The orchid rail and "AI · Posted" stay: the preparer.
   - `meta` reads "posted by you": the approver.
   - `actions` is gone, so the block can't be posted twice.
   - Beneath it sits the run log row for the posting step, `passed`. The green appears only there, where something true happened.
   - It needs no library change.
3. **Every component page has a pair, and the pair proves the component's decision line.** The wireframe draws one page; the same layout serves all ten. The draft pairs below are owner copy to review:

| Component | Before | After |
|---|---|---|
| Chat starter | Suggestions listed | One picked: the composer is filled, nothing sent |
| Chat composer | File uploading, Send held | Uploaded, Send ready |
| Agent reasoning | "Thinking…", folded | Done, opened to its steps |
| Agent plan | Drafting a step, actions disabled | Ready, Run plan enabled |
| Lineage tree | The figure | Opened down to its entries |
| Attachment row | Uploading | Ready; the name is the link |
| Agent block | AI · Awaiting review | AI · Posted, posted by you |
| Chat thread | Question asked, "Working…" | The answer grown in the same place |
| Run log row | Failed row, closed | Opened to its error |
| Status badge | AI working | proposed |

The wireframe's Storybook link, "Proposed, approved and rejected states in Storybook ↗", promises stories that don't exist: AgentBlock's are Default, Awaiting review and Grayscale. Each page links by name instead, for example "Agent block in Storybook ↗", to that component's Docs page.

**D3. Grounds — bands decided 2026-10-25, plates and the closing band 2026-10-26 (owner): (c), dark for single specimens.** The wireframes draw grey in two places, and they're separate questions. In light mode, canvas, surface and raised are all `ledger-50` (§3, "Paper on paper"), so the theme has no second paper tone, and lint rejects raw ramp names in `apps/`.

1. **Section bands: rules only.** No band is tinted anywhere. Sections are separated by a full-width 1px `--color-border` rule (§0 rule 7, "Borders do the work whitespace does elsewhere"). `--color-bg-hover` is not a band colour: it's the interaction overlay, and a hovered row inside a hover-tinted band would composite to 12% and look different from one outside. A real band tone would be a library token for one site's decoration, and is not added.
2. **Specimen plates: (c), dark for single specimens**, chosen from the comparison PR 2 built at `/plates`, with real components, at desktop width and on a phone. The hero and each component page sit on a dark plate; the Components grid stays on paper. The three options compared were:
   - *(a) Paper plates:* a 1px frame on paper. Nothing new, every contrast figure already measured. The risk is paper on paper on paper, with 15 cards reading as one flat sheet.
   - *(b) Dark plates:* each plate sets `data-theme="dark"`. `theme.css` scopes dark mode as `[data-theme='dark']`, not `:root[…]`, so every token recomputes inside the plate, and the components show in the mode they were designed for. The plate must set its own text colour, since inherited text comes from the light page. Contrast is then checked on two grounds per page. The risk is 15 dark rectangles making Components heavy.
   - *(c) Dark for single specimens:* dark on the hero and the component pages, where one specimen is the subject; paper in the Components and Home grids. The cost is two plate styles to keep consistent.

   To-build cards (dashed frame, "Not built yet") follow whichever ground is chosen.
3. **The hero: a paper plate on a ruled sheet. Revised 2026-10-26 (owner), as a prototype for review on the preview.** On the live hero, the dark plate read first and the headline second in a squint test. Its ground is the headline's own ink, 16.39:1 against the page, over about 756×386px. The orchid rail and the "AI · Awaiting review" label disappeared inside it, and its 1.62:1 frame couldn't be seen beside it. A dark block on paper also reads as a hole in the page rather than a sheet on it. (a) had been turned down for paper on paper on paper. A ruled hero removes that risk, because the plate is the one place in the hero without rules:
   - **The sheet.** The hero is ruled like a spreadsheet: 1px lines in `--color-border`, the colour of the section rules, so no token is added, on a layer at 60% opacity, which measures 1.16:1 on paper. At full strength (1.29:1) the owner found the ruling a little strong on retina and non-retina screens alike (2026-10-26). Rows are `--h-row-sm` (28px), `DataTable`'s row height. Columns are the 12-column grid's pitch, aligned to the rail, so a column line runs down the left edge of every column. Under 768px a line runs down every other column, 6 across: twelve 30px columns on a phone ruled near-square cells, which read as graph paper and crowded the lead, while every other column gives cells about 61×28, the shape of a spreadsheet's. **Column lines are element borders on a CSS grid with the rail's tracks, not a background.** A repeating gradient puts a line wherever the arithmetic lands, and between breakpoints the pitch isn't a whole pixel (100.67px at 1280px), so lines fell between device pixels and drew soft (owner, 2026-10-26). The browser snaps a border to a whole pixel. Rows stay a gradient, because 28px is always whole. The lines fade out toward the hero's edges, so the sheet has no hard border against the rule-only bands below.
   - **The plate** is paper, opaque over the rules, in `SpecimenFrame`'s own 1px `--color-border-strong` frame, the same as the Components cards. A frame in `--color-text-primary`, the headline's ink, read heavy (owner, 2026-10-26), as the full-ink focus ring had (design system §4). Against rules at 1.16:1, the frame's 1.62:1 reads as an edge.
   - **Settled: one filled button.** On a paper plate, "Open the demo" and the specimen's "Post entry" were both ink at the same weight (owner, 2026-10-26). The hero became a teaser the same day (D6, changed), with no Post entry, so "Open the demo" is its only filled button.
   - **Only the hero is ruled.** On the other pages a ruled band would compete with the section rules.
   - **The rules are decoration.** They're `aria-hidden`, and they drop out in forced colours, where the plate's frame still draws its edge (D4, §11).
   - Component pages keep their dark plates, so the site still shows the components in dark mode, the mode they were designed for.

**The closing band is dark**, decided with the plates. It isn't a tint: it's a section set to `data-theme="dark"`, with no new token, and it sets its own ground and text colour.

**D4. Colour mode — decided 2026-10-25 (owner).** Page mode and specimen mode are separate axes: `[data-theme='dark']` scopes to any element, so a light page can hold dark specimens. D3 decides specimen mode from PR 2's screenshots. This decides the page.

1. **The page is light only.**
   - `<html data-theme="light">` ships in the prerendered HTML. The site never calls `useTheme()` and never reads the OS preference (`tools.md`, "Styling and tokens").
   - The product is dark-first because of multi-hour working sessions (§0 rule 8). A site visit is minutes of reading, and the art direction is ink on paper.
   - Following the OS would double every check. It would also need a blocking script in `<head>` to avoid a flash, and it would tangle with D3, since a dark plate disappears on a dark page.
2. **Wherever a value differs by mode, Foundations shows both, side by side.** Dark and light are not mirrors (§0 rule 4), so one mode documents half the system:
   - All of Color.
   - Typography's text colour samples. Sizes don't change by mode and appear once.
   - Color's surfaces and overlay sheet: paper on paper drawn by a rule in light, the `ledger-925` step in dark (§4 "Elevation"), and Density's border samples.

   Side by side, not a switch: the comparison is the content. Each dark sample is a container set to `data-theme="dark"` that sets its own ground and text colour.
3. **The site must read in forced colours** (Windows high contrast), which removes backgrounds and shadows. Borders carry the structure (§0 rule 7). The check is in §11.

**D5. The stories and their figures — decided 2026-10-25 (owner).** None of the wireframes' figures are in the data: no ¥184m gap, no ¥121m Tsukuba variance, no account 5900, no ¥12.6m rebate accrual, and no "Operating profit, Sep, ¥312m". September operating profit was ¥819m against a ¥794m budget, ahead rather than behind (`lastMonth` in `packages/ui/src/fixtures/kasane.ts`). A site whose second principle is "Every number opens down to the entry behind it" opens with figures that have entries behind them.

1. **The hero and the Agent block tell the duplicate payment** (`apps/demo/data/findings.json`, `duplicate-payment`).
   - AP says the system blocks a duplicate supplier invoice number in every entity. KUS entered supplier invoice MFL-58821 twice, as API-KUS-2607-00007 and API-KUS-2607-00011, $48,216.40 each, and paid both. The sources are `05_interview_ar_ap_2026-10-14.txt` and `supplier_invoices_fy2026_h1.csv`.
   - The agent proposes reversing API-KUS-2607-00011, so the supplier owes the amount back. A person posts it.
   - *Changed 2026-10-26 (owner review):* the question is "Did we pay any invoice twice?" ("this half" assumed the reader knows fiscal halves). The answer leads in plain words, "Invoice MFL-58821 was entered twice and paid twice, $48,216.40 each time", and the entry ID moves to the smaller source line. The proposed entry reads "Reverse the duplicate payment". The entity code and the first entry's ID no longer show, and the source line cites the invoice file only.
   - Why this story: the figure is exact, and the correction posts in October, which is open. The risk is plain, since money left the company. And the finding contradicts a person's claim, which is why a person decides.
   - The September cut-off (`revenue-cut-off`) was the first proposal and was set aside. September was locked on 8 Oct 2026 (`close-length`), so its correction would need explaining.
2. **Lineage tree, Agent reasoning and Chat thread tell the H1 gap.** H1 operating profit was ¥2.2bn against a ¥2.5bn budget, ¥355m under. `operatingBridge` splits the gap into six named steps, and exchange rates account for ¥317m of it (the two FX steps, summed in code). Together the two stories cover both halves of the product's promise: explain the numbers, and stop before changing the books.
3. **Prose is compact; parts beside their total are exact.**
   - Rounded separately, the bridge's two FX steps show as ¥41m and ¥275m, which add to ¥316m. Their exact sum rounds to ¥317m. A total that doesn't match its displayed parts is a footing error, and finance readers distrust the whole screen when they see one.
   - So a sentence says "¥317m", while a lineage tree or a table shows exact yen (¥316,748,831 beside ¥41,415,809 and ¥275,333,022), and its parts always add up.
   - `docs/agent-voice.md` quoted "¥316m of the ¥355m shortfall", the sum of rounded parts. It's corrected to ¥317m.
4. **The posted entry's journal number is computed, never typed.** `export-fixtures.mjs` derives the next number in KUS's October sequence from the general ledger's journal, in the format `JE-KUK-2608-00055` uses (A5). As generated on 2026-10-26 it is `JE-KUS-2610-00040`: October already holds 39 KUS entries, because the data runs to 15 Oct.

**D6. The hero rests — decided 2026-10-25 (owner).** The wireframe note (`76:45`) says the hero "Plays once on load". The site is prerendered, so a specimen ships one frozen frame, and that frame is all a crawler, a link preview, a visitor without JavaScript or one with reduced motion sees. If that frame is the resting proposal, autoplay means JavaScript rewinds it to an empty plate and plays forward, on the most-viewed spot of the site. If it's the first frame, every link preview shows a question with no answer.

The headline's claim is that an agent stops. A hero that is already stopped, waiting for the visitor, shows that claim, where an animation would only end on it. The visitor is the person the agent is waiting for.

1. **On load the hero rests on the proposal**: the question, the cited answer, and the `AgentBlock` with Post entry, Edit entry and Don't post. Nothing moves.
2. **The one motion is the visitor's.** Pressing Post entry sets the label to "AI · Posted" and `meta` to "posted by you", removes the actions, and writes the run log row (D1, D2).
3. **Then a single control appears: Replay.** It plays the whole run (question, answer, proposal) in 5 seconds or less, and stops at the proposal, waiting again.
4. **The run log row's space is held by a dashed slot** reading "Run log row is written here after Post" (draft copy). Dashed means placeholder (§7.8, "Border style"). The slot keeps the page from jumping when the row arrives, and says what Post will do before it's pressed.

*Changed 2026-10-26 (owner review):* the hero is a teaser. Website heroes are rarely interactive, and visitors miss it. It rests on the waiting proposal with no buttons, and Replay, always shown, plays the run back to it. Post entry, Edit entry and Don't post (items 1–3) stay on the Agent block card. The dashed slot (item 4) is removed everywhere, because readers didn't understand it.

Specimens below the first screen play once as they scroll into view, from a frame nobody has seen yet, so nothing visibly rewinds (§6).

- `demo.tabularui.com` is a five-step onboarding journey (`apps/demo/README.md`). The visitor plays Kasane's Head of FP&A and loads 20 files. A scripted agent reads them, then lists what it understood, the contradictions, the gaps, and questions to ask.
- It uses 4 of the 10 built agent components, proposes no entries, and runs no September close. Neither wireframe line is true of it.
- The duplicate payment the hero shows (D5) is one of the contradictions the demo finds, so the band links the two.

| Slot | Copy | Source of each specific |
|---|---|---|
| Heading | Give an agent a finance team's files. | — |
| Line | Kasane is a fictional printer maker. You play its Head of FP&A while a scripted agent reads 20 of its files. The duplicate payment above is one of the contradictions it finds. | The title from `apps/demo/data/company.json` (`persona.title`); "20" computed from `pack.json`; the finding from `findings.json` (`duplicate-payment`) |
| Action | Open the demo ↗ | The arrow is `aria-hidden`; the link's name is "Open the demo" |

- **"Scripted" stays.** A visitor's own files get no findings, so copy that only says "an agent reads" would promise analysis the demo doesn't do.
- **The band closes Home only**, where "the duplicate payment above" is true. Other pages end at the footer.
- The copy was reviewed with the Tabular UI copywriter rules: no banned words, and each sentence 15 words or fewer.

**D8. The nav — decided 2026-10-25 (owner).** The wireframes draw a floating bar (`75:25`): inset 32px from the sides and 16px from the top, 56px tall, with a 1px rule all round. Mobile (`75:46`) is a 48px bar, inset 8px, holding the wordmark and a "Menu" button.

1. **A site-built nav, in `apps/site`, drawn to the wireframe.** The library's `AppBar` was considered and not used: it's a full-width sticky band. The site nav still follows what `AppBar`'s README records, because each item there is a failure that already happened once:
   - Links are real `<a>` elements styled with `buttonVariants`, never Base UI's `Button`, which would announce a link as a button.
   - The list carries `role="list"`, because Safari drops list semantics from an unstyled list.
   - The current page gets `aria-current="page"` and weight, styled with the bracketed `data-[active]:` form, not the shorthand.
   - The landmark is one `<header>`, holding a `<nav aria-label="Main">`.
2. **It is inset and scrolls away; it doesn't stick.**
   - Nothing scrolls under it, so its fill is solid `--color-canvas`, with a 1px `--color-border` rule on all four sides. Translucency would have nothing to show.
   - A bar that scrolls away can't cover a focused element (WCAG 2.4.11), so no `scroll-padding-top` is needed.
   - Long pages rely on their own navigation once the bar is gone: the Components jump index, the component jump menu, and the footer.
3. **Demo ↗ is 36px, not the wireframe's 40px.** Controls are capped at 36px (`CLAUDE.md` rule 6), so it's `buttonVariants` at `size="lg"`. The bar's 56px height is space around controls, not a control, and stays.
4. **Mobile: composed in `apps/site`.** Below the breakpoint, the links hide and a "Menu" button opens the library's `Menu`, listing every nav link and the three external ones. The trigger is the library's `Button`, since lint rejects a `<button>` outside `foundational/`. `AppBar` still has no responsive collapse (its README, "Not implemented"). If a second consumer needs one, this pattern is the candidate to promote into the library.

## 1. What the site is for

tabularui.com is the public front of Tabular UI for designers and engineers deciding whether to use its agent components. A visitor should leave knowing three things: the three principles, what each of the 15 agent components does (seen working on realistic data), and how to install one.

It is not the reference. Storybook (`storybook.tabularui.com`) holds every component, prop and state, and the site links to it rather than repeating it. It is not a sales page: there is no pricing, no sign-up, and no analytics, cookies or tracking.

**The 15 are a subset.** The library has 44 components: 18 foundational and 26 product (`docs/components.md`). The site presents the 15 that make up an agent run, grouped into five moments, 10 built and 5 to build. The Components page says so in one line and links to Storybook for the rest.

**The wireframes give layout, not values.** They are greyscale, and they predate this spec. Their frame names and notes cite "P" numbers from the retired patterns doc, and their Color page shows placeholders and the wordmark's colours. Ignore both. Where a wireframe and the library disagree on how a component looks, the library wins: the hero's agent block is drawn as a bordered card, and the real `AgentBlock` is a neutral box with an orchid rail. ## 6. Specimens

**One player for every live specimen.** A specimen is a list of states, each with a time, rendered with real components. The last state is the **rest frame**: the decision the specimen exists to show.

- **The prerendered HTML is the rest frame.** Visitors without JavaScript, search crawlers, link previews and reduced-motion users all see the decision.
- **A specimen below the first screen plays once** when half of it first enters the viewport, from the first state to the rest frame, and then stops. Nothing loops.
- **5 seconds or less.** A sequence that starts on its own and runs over 5 seconds needs a pause control (WCAG 2.2.2). Under 5 seconds it doesn't, so the cap removes the control instead of adding one.
- **Replay** is a library `Button`, `variant="outline"` `size="sm"`, inside the plate at the bottom right, named for its specimen: "Replay Agent block".
- **Reduced motion:** the rest frame only. Replay jumps to the rest frame.
- **One announcement.** A polite live region announces the final state once ("Posted"), never each step. It empties after it has been read, as `AgentReasoning` does with its own region.
- **No randomness, no network, no AI.** A specimen is a script.

**The hero** (D5, D6) is a teaser since 2026-10-26: it rests on the question and the waiting proposal, with no buttons and no slot, and Replay plays the run back to it. Everything below describes the **Agent block card**, which keeps the decision. (Until then it described the hero, and a dashed slot held the run log row's space.)
- Pressing Post entry changes the block's label to "AI · Posted", sets its `meta` to "posted by you", removes its actions, and writes a run log row beneath it, `passed` (D1, D2).
- Replay then plays the run from the question back to the waiting proposal, in 5 seconds or less.
- **Don't post** (decided 2026-10-26, owner) declines as Post accepts:
  - The label becomes "AI · Not posted", with `meta` "declined by you".
  - The buttons go, and a `skipped` run log row naming the invoice appears: nothing reached the books.
  - It is announced once ("Not posted."), and Replay appears.
- **Edit entry** (decided 2026-10-26, owner) turns the entry's memo and period into the library's `Field` and `Input`, with Done and Cancel.
  - Done returns to the proposal showing the change, still waiting for Post.

- After Post or Don't post, focus moves to Replay. After Replay finishes, focus moves to Post entry and "Awaiting review." is announced. Focus is never dropped on the page.

## 7. Site layout and type

The site is a reading page, not dense product UI, so it keeps a few values of its own. **They live in `apps/site`, never in `packages/ui`.** They cover only space and size. Every colour, radius, border, shadow, weight and font comes from the library's tokens.

**Grid** (from the wireframes):
- 12 columns with 24px gutters.
- Page margins of 16px under 768px, 32px from 768px, and 48px from 1200px.
- A 1344px content width.
- A 1040px reading column for Principles and component pages, and 680px prose blocks.
- Cards span 4 columns (432px), the hero splits 5/7, and the five moments are their own 5-up row with 16px gaps.

**Rhythm:** sections are padded 48px under 768px, 64px from 768px and 96px from 1200px, and separated by a full-width 1px `--color-border` rule. The hero is ruled as a sheet in the same colour at 60% opacity: 28px rows, columns on the 12-column pitch, every other column under 768px (D3, item 3).

**Tokens.** These are the site's only custom properties. The `--site-` prefix keeps them apart from the library's names, so none can shadow a library token:

```
--site-pad-x        16px · 32px ≥768 · 48px ≥1200
--site-section-y    48px · 64px ≥768 · 96px ≥1200
--site-gap          24px
--site-gap-tight    16px
--site-w-wide       1344px
--site-w-reading    1040px
--site-w-prose      680px
```

**Type.** Headings are serif with no extra work: `theme.css` sets every `<h1>`–`<h6>` in `--font-heading` (§8.3). The library's scale stops at 32px (§8.1), so the site adds reading sizes in `apps/site`, in rem (§0 rule 10):
- Display: 64px desktop, 40px mobile.
- Section heading: 44px and 30px.
- Card title: 20px and 18px.
- Lead: 18px.
- Body: 16px.
- Small: 14px.

Weight never exceeds 600. Each size is declared with its line height. Each is also added to the site's tailwind-merge config, or `cn()` will read it as a colour and drop the text colour (failure log, `text-metric`).

**Inside a specimen, nothing is scaled.** Components render at their own 13px base and 32px control height. A specimen shows the product as it is.

**Mono shows data only:** IDs, file names, tokens and times. Labels are sans.

## 8. Library rules on the site

`eslint.config.js` already applies the full design gate to `apps/*/src/**`, and allows frame spacing only in `apps/*/src/App.tsx`, capped at 64px. The site's 96px section padding fails it, as it should until this spec is approved.

**The change (A3), as built in PR 1 (2026-10-26).** It turned out smaller than planned:
- **No spacing exception was needed.** The gate caps named utilities (`p-10`) and bracketed lengths (`py-[96px]`). A value held in a token, `py-[var(--site-section-y)]`, carries no length for it to read. A probe through `eslint --stdin` as `apps/site/src/routes/Probe.tsx` showed the token line passing, with all six deliberate violations failing: a spacing multiplier, a bracketed 96px, a raw hue, a 12px radius, `--pad-frame-x` outside `App.tsx`, and a hand-made `<button>`. A regex gate fails open, and silence looks like a pass, which is why the probe ran.
- **What the site needed instead was a `react-refresh` block.** React Router route modules export `meta`, `Layout` and other route functions beside the component. `react-refresh/only-export-components` flags those, so a block for `apps/site/src/**/*.tsx` lists them as allowed names.
- **Route modules live in `src/`** (`appDirectory: 'src'` in `react-router.config.ts`), not React Router's default `app/`. The gate covers `apps/*/src/**`, and route modules in `app/` would have skipped every rule with no error.
- The generated `apps/site/build` and `apps/site/.react-router` are ignored by ESLint and Prettier.
- Stylelint runs on `apps/*/src/**/*.css` with the same rules and no rule change: the caps read raw `px`, so values held in `--site-*` tokens pass and raw ones still fail.

**Never change `packages/ui` to make the site work.** If a component is missing something, stop and raise it: a library change is its own decision.

## 10. CI

`Verify` is the one required check. A separate workflow that runs only when certain paths change can't be required, because GitHub waits for it forever on PRs where it doesn't run. So the site runs inside `Verify` (A4):

- **Site-only PR:** install, lint, type-check, build the site, run the site's Playwright tests. The story tests, visual regression and design system specs are skipped. Target: under 6 minutes, against 25–27 for the full run.

**Step 3, as built (2026-10-26):**
- **The Foundations pages read the tokens at build time.** `src/tokens-parse.ts` reads `theme.css` as the package ships it (`tabular-ui/theme.css`) and `docs/palette.json`. It resolves each role's step per mode, computes contrast on each mode's canvas, and takes each scale token's value and its own comment from `theme.css`. `tests/tokens.spec.ts` pins the parser to figures the design spec states (`sage-700` at 6.23:1, `ledger-50` at 16.39:1, `ochre-500 / 10%`, `ledger-925`), so a parser reading the wrong block fails the build.
- **Swatches paint the real token utilities** (`bg-fill-danger`, `text-text-warning`). The ramps alone paint `palette.json`'s measured hex, because no token names a raw step.

**Links, as built (2026-10-27, owner):** two rules. A link inside a sentence is sage and always underlined (`textLink`). A link that stands alone is ink at rest, in its context's colour, and sage on hover, with no underline (`standaloneLink` in `src/lib/styles.ts`). A 1px underline was tried first: it's the thinnest line that renders the same on every screen, and it was still too heavy. Standalone links include the footer, card titles, the jump index, a component page's links and its previous and next, and the links on Principles and the 404. The nav keeps its ghost buttons: they're buttons, not text links (owner, after trying them as text links). Buttons (the hero's actions, Replay) and the component tags keep their own styles. `tests/pages.spec.ts` checks the rest and hover styles on a card, jump-index and footer link against a text link's sage.
