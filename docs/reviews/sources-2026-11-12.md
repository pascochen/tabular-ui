# Sources: how it could help the Group Controller (2026-11-12)

Six methods from Ileana Marcut's UX + AI method library, run on the demo's Sources view (`apps/demo/src/views/Sources.tsx`), then a benchmark of 32 screens from Mobbin (section 7). The library's AI product principles are the standing quality bar. This is a brainstorm: it ends in a concept to build, not a list of defects.

Seen in the local build at 1280×800, light mode, on the branch that holds the Tasks changes (`docs/reviews/tasks-2026-11-12.md`): `?view=sources`, a text file and a table opened from a finding, and one switch turned off, then Tasks.

**These are hypotheses.** No research on Sources exists. The needs in section 3 are read from the role and the script, and each is marked [assumed].

## The new context

Tasks now tells Daisuke Onodera, Group Controller, whose move each finding is. Three things in it point at Sources:

- A row says "1 not checked". The count comes from what the agent couldn't read.
- The panel shows the question he owes an answer to, and under it the files the finding rests on. Each opens Sources at its records.
- Turning a file off in Sources raises a row's count in Tasks. Checked: with `accounting_policies.md` off, "Revenue booked early" reads "2 not checked".

So Sources sits inside one loop: **Tasks → the claim → the record → back to answer.** He is in Sources for a minute, between reading a claim and vouching for it. He also set the agents up, so Sources is where he decides what they may read.

## What the page is today

- A list of 9 file names in two groups, Documents and Data.
- The open file: its name, one line on what it covers, a switch labelled "Agents read this", the findings that use it, an honest count of the extract ("Showing 18 of 8,313 rows, 8 of 16 columns"), and the extract with the finding's records tinted.

## 1. Quick clarity check

**First read.** A file browser for what the AI agents read. I can open a file and switch it off for the agents.

**What's unclear, worst first**

1. **The tinted rows don't say what they prove.** In `ar_aging_monthly.csv`, 8 of 18 rows are tinted. The claim, "over its $600,000 limit at 8 month-ends before the credit hold", is on another page. The largest balance, 1,422,722.93 for 2026-09, is not tinted, and nothing here says why.
2. **The switch doesn't say what it does.** Turning it off changes the switch and nothing else on the page. The effect lands in Tasks, in the agent's profile and in the finding's panel.
3. **The list is names only.** It doesn't say which agent reads a file, which finding rests on it, what period it covers, or whether it's switched off.
4. **"Used by" is empty for a file an agent reads but no finding cites.** `close_calendar.md` looks unused. Revenue AI reads it.
5. **"Agents read this" is plural and in the present tense.** One agent reads most files, and the findings were made at 09:04. Does off mean "stop reading" or "pretend you never read it"?
6. **What the agents couldn't read isn't here.** The page lists what exists. The delivery notes and the employee master, which two findings say they lack, appear nowhere.

**Top 3 fixes**

1. State the finding's claim above its records.
2. Say what the switch changes, beside the switch, before and after.
3. Give each list row the agent that reads it and its off state.

## 2. AI control and boundaries review

**The feature.** Sources shows the files four agents read and lets the Group Controller switch each off. Kept apart:

- **Automation:** the agents read their files and made their findings at 09:04, unasked.
- **Suggestion:** none on this page.
- **Decision:** which files the agents may read. His, through the switch.

**The evaluation**

- **Where should it stop?** Switching off a file that a finding waiting on his answer rests on. With `accounting_policies.md` off, the question "Where should the ¥42.7m correction go?" still stands, and its basis is a policy the agent may no longer read. Nothing pauses or warns.
- **What should it never do?** Change a figure when a source goes off. It doesn't, which is right. The page doesn't say so.
- **When should it ask?** Before a switch takes effect on a file findings rest on. `PRODUCT.md`: a gate says what changes and who it reaches before it runs. This control has no gate and no statement.
- **When should it say "I don't know"?** The extract count does, well. What it can't say is which claims the extract is too short to support. "The only one of the 887 September invoices" can't be checked against 11 rows.
- **What stays with him?** What the agents read. But he can only take a file away. The "not checked" lists ask for files he can't add.
- **Where could it mislead?** (a) Tinted rows read as "verified" when they are "cited". (b) A file with no "Used by" reads as unread. (c) The list shows a switched-off file exactly like the others.
- **Where might he feel unsure?** After every switch: the page gives no sign that anything happened elsewhere.
- **What breaks trust over time?** Switches he forgets he flipped, since only the open file shows its state. And a "not checked" count in Tasks that rises with no trace of why from here.
- **Different behaviour for similar inputs?** An unknown `?source=` opens the first file as if it were chosen. Tasks did the same until today's fix.
- **Unhandled edges?** A file that changed after the agents read it, a file two agents read with only one finding, a finding whose every source is off. The first isn't in the data. The other two can be reached and say nothing.

**Top 3 risks**

1. **A control with invisible consequences and invisible state.** It changes three other screens and shows on none of the nine list rows.
2. **Cited evidence that reads as checked evidence.** Tint without the claim, on a trimmed extract.
3. **The gaps are missing from the page about coverage.** He can see every file read and none of what wasn't.

**Improvements**

1. Beside the switch, one line of fact: who reads the file and which findings rest on it. After turning it off: what can no longer be rechecked.
2. Show off in the list, in words.
3. Put the claim and its "not checked" lines over the records.
4. Say per claim what the extract holds and what it leaves out.

## 3. How might we

Needs, all [assumed] from the role and the script:

**N1. Check an agent's claim against the record before answering for it.**
- How might we let him see the claim and the record in one glance?
- How might we make "cited" and "checked by you" two different things on screen?
- How might we tell him when the record shown is too short to support the claim?

**N2. Know what the agents could not read before he signs.**
- How might we make a gap as visible as a file?
- How might we tell him which gaps he can close and which wait on someone else?

**N3. Trust that the evidence is the right version, for the right entity and period.**
- How might we show what each file covers without opening it?
- How might we tell him when a file changed after an agent read it?

**N4. Control what the agents read, and see what that does.**
- How might we show the cost of switching a file off before he does it?
- How might we keep every switch he flipped in view?

**N5. Get back to the decision without losing his place.**
- How might we carry the question he owes with him into the record?
- How might we make the way back one step?

## 4. Eight rough takes

Goal: he can vouch for a finding. He sees what it rests on and what it lacks, and he controls what the agents read.

1. **Unit: the claim.** Opened from a finding, the file shows the finding's sentence and rule over its records, with "Answer in #revenue" beside it.
2. **Emphasis: what's absent.** A third group in the list, "Not checked", holds what the agents said they couldn't read, each tied to its finding.
3. **Picture: a coverage map.** Entities across, months down. Each file is a band, and a hole is a hole.
4. **Entry point: the agent.** Files grouped by who reads them, so each agent has a reading list he can edit.
5. **Time: chain of custody.** Each file says when it was read, by whom, and whether it has changed since.
6. **Mechanism: the switch as a gate.** Turning a file off first says what changes and who it reaches, then applies.
7. **Density: only the evidence.** The cited records and their neighbours show. The rest of the extract folds behind "10 more rows".
8. **What it leaves out: the page.** No Sources place. A file opens in the right panel beside the task or thread, and he never leaves the decision.

## 5. Analogous inspiration

The job, stripped of finance: **let someone who must vouch for a claim see what it rests on, what is missing, and whether the evidence still holds, in under a minute.**

1. **The court bundle.** Every assertion in an argument cites a numbered exhibit and page, and the exhibit carries the label of the argument that relies on it.
   - Same job: the reader must test a claim against a document, quickly, and both sides of the link are marked.
   - Adapt: the record carries the claim that cites it. Take 1.
2. **Museum provenance.** A record of an object's owners lists the gaps as entries: "whereabouts unknown" for a stated span.
   - Same job: a gap that is written down can be weighed. A gap that is left out reads as none.
   - Adapt: "Not checked" lines become entries in the list of sources. Take 2.
3. **The aircraft's deferred-defect list.** An aircraft may fly with a listed item inoperative, provided the item is placarded where the crew will see it and the limits that follow are stated.
   - Same job: working without one input is allowed, and the cost is stated where the decision is made.
   - Adapt: a file switched off is marked everywhere it matters, with what can't be relied on. Take 6.
4. **Forensic chain of custody.** An evidence bag's label records who held it and when, and whether its seal is intact.
   - Same job: the evidence is only as good as the proof that it hasn't changed since it was examined.
   - Adapt: each file says when an agent read it and whether it's the same file now. Take 5. The data has no read time per file, so this waits.
5. **The survey map.** Old survey sheets mark unsurveyed ground as unsurveyed. They don't draw it as empty land.
   - Same job: a reader plans from the map, so the map must separate "nothing there" from "not looked at".
   - Adapt: the coverage map. Take 3. It needs each file's entities and periods as data, where today they are one line of prose.

## 6. Concept stress test

The concept, from takes 1, 2 and 6 with the list fix:

- Opened from a finding, the file shows the finding's claim, rule and "not checked" lines over its records, with the way back to answer.
- The list gains a "Not checked" group, one entry per gap, tied to its finding.
- Each list row says which agent reads the file and, in words, when it's off.
- Beside the switch, a line says who reads the file and which findings rest on it. Off, it says what can't be rechecked.

**A skeptical Group Controller**

- "You put the agent's sentence over rows the agent picked and tinted. That's the agent marking its own work. I'll nod, not check."
- "'The only one of the 887 September invoices' sits over 11 rows. Your pinned claim makes a short extract look like proof."
- "'Not checked' lists a missing employee master next to Legal's pending decision. One is a file I can go and get. The other isn't a source at all."

**An engineer**

- "`notChecked` is prose in `close.json`. To key a list entry or a link on it, the dataset needs a kind and a target per line, and the dataset is outside this repo."
- "The claim shows only with `&item=`. Browsing to the same file shows none. That's two pages under one URL shape, and the switch line has to make sense in both."
- "`AttachmentRow` takes a name and a size. An agent, a count and an off state in a 22rem column is a different row, or a change to a product component."

**The owner**

- "Tasks' panel already shows rule, evidence, sources and 'not checked', through the `Sources` component. Now the page repeats it by hand. Which one is the pattern builders copy?"
- "The switch line is demo copy. If the control needs a consequence statement, that belongs in a component with a README, or it's a one-off."

**The most fatal: the short extract.** The concept's promise is "check the claim against the record". For a claim about what is present, the extract holds the record and the promise is kept: 8 months over the limit, two entries of one invoice. For a claim about what is absent, "the only one", "paid once", the record is the 876 rows not shown. Pinning that claim over 11 rows turns an honest count into a false comfort. The concept survives only if each claim says which kind it is: "These rows hold the invoice. The other 876 aren't shown, so 'the only one' can't be checked here."

**What none of them does**

- **None says what the evidence shown can't support.** Elicit shows the supporting quote. No screen says "this extract is too short to show the claim". The stress test's fatal objection has no precedent here, so that line is ours to design.
- **None lists what the agent wanted and couldn't read.** Vanta's gaps come from a compliance checklist, and Intercom's from a list of integrations. A gap the agent itself reports is new ground.
- **Almost all are setup pages.** They serve the person who feeds the agent: upload, sync, retrain. Only Elicit serves the person who checks the agent. That confirms the direction, and it means the benchmark is thin where the concept is strongest.

**What changes in the concept**

1. Add a count and a step control to the claim over the record: "1 of 8", Previous, Next (Elicit).
2. Put state, reader and "used by" in the list as columns or words (Intercom, WRITER, Xero). At nine files the list could be a `DataTable`.
3. Keep the switch's consequence in view after the change, not only before it (Chatbase, Origin).
4. When the "Not checked" group is built, give each gap an owner and a date where the data has one (Vanta). Legal's decision has both: "by 30 Oct".

## Conclusion

- **Sources should be where he vouches, not where he browses.** Today it answers "what files exist". In the loop Tasks now sets up, he arrives with a claim and a question, and needs "is this true, what's missing, and can I answer now".
- **Build the claim over the record first** (take 1). `rule`, `evidence`, `notChecked` and the hero's question are in `close.json`, and `&item=` already says which finding he came from.
- **Say what the extract can't show.** This is the stress test's condition for the first point. A claim of absence over a short extract must say it can't be checked here.
- **Make the switch state its effect and its state.** Who reads the file and which findings rest on it are derivable today. "Off" belongs in the list, in words.
- **Give the list who reads each file.** It fixes the empty "Used by" on `close_calendar.md`.
- **A "Not checked" group is the strongest idea and the least ready.** The lines are prose, and one of the three is a pending decision, not a file. It needs a kind per line in the dataset first.
- **From the benchmark:** step through the cited records ("1 of 8"), say state and reader in the list, and keep the switch's consequence in view after the change. No screen says what its evidence can't support, so that line has no precedent.
- **Leave for later:** read times and changed-since (not in the data), the coverage map (needs entities and periods as data), files in the right panel beside the thread (a shell change).
- **Small and separate:** an unknown `?source=` opens the first file as if chosen, the same fallback Tasks had.
- **Not run:** JTBD extractor and Research synthesis, which need real sessions. A usability test of the Tasks → Sources → answer loop would turn these hypotheses into findings.

## Built, 2026-11-12

- **The claim over the record.** Opened from a finding, the file shows the finding in the agent's `AgentBlock`: what the books show, the rule and what wasn't checked. The button to the thread is primary while he owes an answer.
- **What the extract leaves out.** Under the claim: "This finding rests on 1 of the 11 rows shown. The file's other 876 rows aren't shown, so a claim about the whole file can't be checked here." The same line for every finding, from the file's own counts. It doesn't judge which claims are about absence: the data has no kind per claim.
- **The switch states its effect, before and after.** "Revenue AI reads it. Revenue booked early rests on it." Off: "Off. Revenue AI doesn't read it. Revenue booked early can't be rechecked."
- **The list names each file's reader** and says "Off" in words.
- **The word is "rests on", not "cited".** `close-data.spec.ts` keeps "cited" out of the demo's source, so the page says what a finding rests on, as the rest of the demo does.
- **Not built: Previous and Next through the selected records.** Every extract in the demo fits on screen with its selected rows, so the control would move nothing. The count is there. The step control is worth building when an extract is longer than a screen.
- **Not built, as planned:** the "Not checked" group, a filter by agent, read times, the coverage map, and the unknown `?source=` fallback.
